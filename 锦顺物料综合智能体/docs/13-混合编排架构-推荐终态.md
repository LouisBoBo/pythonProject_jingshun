# 混合编排架构 · 推荐终态（助手感 + 性能 + 可扩展）

> **定位**：锦顺物料综合助手的 **主架构路径**（取代「纯 Agent 包一切」）。  
> **原则**：**重计算在 Tool / 子流程**；**主 Agent 只做编排与短文本**；**大段结果由画布直连展示**，避免 ReAct 第二轮抄表。

---

## 1. 为什么要混合编排

| 问题 | 纯 Agent 路径 | 混合编排 |
|------|---------------|----------|
| 查数 ~17s + Agent 再抄 50 行表 ~10s | 总 ~28～38s | 快路径 **~17～19s**（无 ROUND 2 抄表） |
| 助手感 | Agent 要么抄表要么改写 | **summary 助手感 + detail 专业呈现** |
| 扩展 ERP / 混合任务 | ✅ Agent 多 Tool | ✅ 复杂任务仍走 Agent |
| 领域分析准确性 | 若挪到 Agent 会降准 | **分析留在子 Chatflow**（Text2SQL + 领域提示词） |
| 未来加能力 | Tool 增多但架构清晰 | **快路径 / Agent 路径** 分流规则固定 |

**结论**：综合智能体 ≠ 所有能力都经 Agent ReAct 输出；**编排分层**才是终态最优。

## 2. 四层架构

```
┌─────────────────────────────────────────────────────────────────┐
│ L0  Router（4 类：DATA | CHITCHAT | REQUISITION | MIXED）          │
└────────────────────────────┬────────────────────────────────────┘
                             │
         ┌───────────────────┴───────────────────┐
         ▼                                       ▼
┌─────────────────────┐               ┌─────────────────────────┐
│ L1a Fast Executor   │               │ L1b Agent Executor      │
│ 纯查数 / 纯追问      │               │ 领料 / 混合 / 寒暄 / 登录  │
│ Workflow 网关 Tool   │               │ ReAct / FC + 多 Tool     │
└──────────┬──────────┘               └────────────┬────────────┘
           ▼                                       ▼
┌─────────────────────┐               ┌─────────────────────────┐
│ L2 Presenter        │               │ L2 Presenter            │
│ Answer 直连变量      │               │ 短 Final Answer + 变量   │
│ summary + detail    │               │ （混合任务可绑 detail）    │
└──────────┬──────────┘               └────────────┬────────────┘
           ▼                                       ▼
┌─────────────────────────────────────────────────────────────────┐
│ L3 Tools & Subflows                                              │
│  invoke_chatflow 网关 | erp_* Custom OpenAPI | 未来业务 Workflow │
│  └─ 锦顺-数据分析子流程（Text2SQL + 分析 + 图表 + 导出）           │
└─────────────────────────────────────────────────────────────────┘
```

### 职责边界（铁律）

| 层级 | 做什么 | 不做什么 |
|------|--------|----------|
| **Router** | **四类**意图分流（DATA 含查询与追问） | 不分查询/追问、不 SQL |
| **Fast Executor** | DATA → 调子助手 API，写会话变量 | 不走 ReAct |
| **Agent Executor** | REQUISITION / MIXED 多步 Tool | 不重写大段表格 |
| **Presenter** | 绑 `summary` / `detail` 到 Answer | 不让 LLM 重生成大段表格 |
| **子 Chatflow** | Text2SQL、领域分析、导出 | 不管领料、不管主会话 auth |

## 3. 主 Chatflow 画布（终态）

> **定稿配置见** [17-主助手路由与传参一览.md](17-主助手路由与传参一览.md)

```
用户输入
  → 意图分类器（4 类：DATA | CHITCHAT | REQUISITION | MIXED）
  → If-Else
      ├─ DATA      → HTTP 子助手 API → Code → Assigner → Answer（detail）
      ├─ CHITCHAT  → LLM → Answer
      └─ ELSE      → Agent（REQUISITION + MIXED）
```

- **DATA** 含新问与「提供明细」；查询/追问由 **子助手** 区分  
- **MIXED** 必须走 Agent（同句查+领）  
- **conversation_id**：会话变量有则 HTTP 自动带，主助手不判追问

## 4. 网关 Tool：`invoke_chatflow`（演进自 `query_material_data`）

MVP 可仍名 `query_material_data`；终态建议统一为 **Chatflow API 网关**，与 [02 §5.2.4](02-ReAct复合智能体设计.md) 一致。

### 4.1 入参

| 参数 | 说明 |
|------|------|
| `question` | 用户问题或追问原话 |
| `conversation_id` | 可选；子 Chatflow API 会话 id |
| `target` | 可选，默认 `material_analytics` |

### 4.2 出参（关键改造）

| 字段 | 用途 | 体积 |
|------|------|------|
| `summary` | Answer 顶部 2～5 句 / Agent Observation（混合任务） | 小 |
| `detail` | 完整表格 + 下载区 + 图表 markdown | 大 |
| `conversation_id` | 追问绑定 | 小 |

**Agent 路径**：Observation **只注入 `summary`**（+ id），`detail` 写入 `last_query_detail`，Final Answer 写短衔接语即可。

**Fast 路径**：Answer **直接绑变量**，零 LLM 抄表。

### 4.3 Code 节点拆分 `summary` / `detail`（网关内）

阶段 6a（可先 heuristic，后接子流程结构化输出）：

```python
def split_answer(answer: str) -> tuple[str, str]:
    text = (answer or "").strip()
    if not text:
        return "未返回结果", ""
    # 启发式：表格前的短段作 summary；全文作 detail
    table_idx = text.find("|")
    if table_idx > 0:
        head = text[:table_idx].strip()
        summary = head if len(head) <= 500 else head[:500] + "…"
        return summary or "查询完成，明细如下。", text
    if len(text) <= 300:
        return text, text
    return text[:300] + "…", text
```

阶段 6b（推荐）：子 Chatflow 在「数据分析」后增加 **Code 输出节点** 或 API 扩展字段，网关直接映射，拆分更准确。

## 5. 会话变量（Presenter 层）

| 变量 | 类型 | 写入时机 | 用途 |
|------|------|----------|------|
| `data_analysis_conversation_id` | String | 每次查数/追问 Tool 返回后 | Fast / Agent 追问入参 |
| `last_query_summary` | String | 同上 | Answer 顶部、Agent 混合任务上下文 |
| `last_query_detail` | String | 同上 | Answer 明细区（直连，不经过 LLM） |
| `auth_token` / `user_profile` | — | 登录 Tool | 领料 |
| `requisition_draft` / `last_material` | — | 领料链 | 多轮确认 |

## 6. 扩展规则（加新功能时）

| 新能力特征 | 走路径 | 封装 |
|------------|--------|------|
| 单 Tool、大响应、无多步确认 | **Fast Executor** + Presenter 绑变量 | 扩 `invoke_chatflow.target` 或新业务 Workflow |
| 小 JSON、单 HTTP | Agent Tool 即可 | Custom OpenAPI `erp_xxx` |
| 多步、需确认、跨 Tool | **Agent Executor** | 新 Tool + Instruction 一条规则 |
| 新 streaming Chatflow | **扩网关**，禁止新建 `_proxy2` | 见 02 §5.2 |

**禁止**：

- 把 Text2SQL / 供应链分析挪到主 Agent  
- 让 Agent Final Answer 重生成 `detail` 全文  
- 每个 API 复制一个代理 Workflow

## 7. 性能与体验目标

| 场景 | 目标耗时 | 用户看到 |
|------|----------|----------|
| 纯查数（Fast） | Tool 时间 + 路由 ~1s ≈ **18～20s** | summary 导语 + 完整表 + 下载 |
| 纯追问（Fast） | 同上 | 同上 |
| 纯领料（Agent） | 视 ERP RTT，多轮可接受 | 确认卡片、短句 |
| 混合「先查后领」（Agent） | 查数 18s + Agent 2～3 轮 | 查数 detail 直连 + Agent 解读 + 领料确认 |
| 寒暄 | **<2s** | 短回复 |

## 8. 与阶段实施的关系

| 阶段 | 内容 | 架构层 |
|------|------|--------|
| 3（当前） | Agent + Workflow Tool 跑通 | 过渡：纯 Agent |
| **3.5** | 意图分类 + Fast 查数路径 + Assigner + Answer 绑变量 | L0 + L1a + L2 |
| 2 / 4 / 5 | ERP Tools、登录、领料 | L1b Agent |
| **6a** | 网关输出 summary/detail/id；追问走 Fast | L2 + L3 |
| **6b** | 子流程结构化 summary（可选） | L3 |
| 7+ | Human Input、SSO | Agent 层增强 |

阶段 3 **可验收**后做 3.5，不必等 ERP。

## 9. 方案对比（为何选混合编排）

| 方案 | 性能 | 助手感 | 扩展 | 结论 |
|------|------|--------|------|------|
| A 纯 Agent | ❌ 慢 | ⚠️ 易改写/抄表 | ✅ | 过渡方案 |
| B 纯 Chatflow 分支 | ✅ 快 | ⚠️ 无统一编排 | ❌ 每加能力改画布 | 不采纳为主路径 |
| C **混合编排（本文）** | ✅ | ✅ | ✅ | **推荐终态** |
| D Tool 只查数 + Agent 分析 | ❌ 更慢更不准 | ⚠️ | ❌ | **否决** |
